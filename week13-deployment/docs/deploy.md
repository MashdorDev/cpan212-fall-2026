# Deploying Campus Events

Three services, each doing one job:

| Piece | Where it runs | Free plan |
|---|---|---|
| Database | MongoDB Atlas | Free cluster, pauses after 30 days with no connections |
| API (`api/`) | Render web service | Sleeps after 15 minutes without traffic, about a minute to wake |
| Web app (`web/`) | Vercel | Hobby plan, for personal and non-commercial projects |

Deploy them in that order: the API needs the database's connection string, and the web app needs the API's URL.

The Render, Vercel and Atlas steps below were checked against their documentation on 2026-09-11. Dashboards change their labels from time to time. If a button has a slightly different name, look for the closest match, and check the linked docs.

## How it fits together

```
Browser ──HTTPS──> your-app.vercel.app                    (pages, and /api/... through the rewrite)
                        │ rewrite /api/:path* and /uploads/:path*
                        ▼
                   campus-events-api.onrender.com ──> Express (NODE_ENV=production, TRUST_PROXY=1)
                        │ MONGODB_URI
                        ▼
                   Atlas free cluster (events, users, rsvps, sessions)
```

The browser only ever talks to the Vercel domain. When it calls `/api/auth/login`, Vercel forwards the request to Render and passes the answer back, including the `Set-Cookie` header. The cookie is saved for `your-app.vercel.app`, so it is a first-party cookie, and every later `/api` call from the browser sends it without any CORS setup. Server Components call the Render URL directly, server to server, for public data such as the events list.

## 1. Atlas

You need the free cluster from Week 9 (`week09-mongodb/docs/atlas-setup.md`).

1. **A database user for production.** In **Database & Network Access**, open the **Database Users** tab and add a user just for the deployed API, with a long autogenerated password. Give it the `readWrite` role on the `campus_events` database only (Atlas lists this under specific privileges), not a built-in role that reaches every database in the project. If this password ever leaks, you can delete that user without breaking your laptop setup.
2. **The connection string.** Copy it from **Connect**, then **Drivers**, put in the new user's password, and add the database name before the `?`:

   ```
   mongodb+srv://campus-events-render:PASSWORD@cluster0.abcde.mongodb.net/campus_events?retryWrites=true&w=majority
   ```

3. **Network access for Render.** Atlas only accepts connections from addresses on the project's **IP Access List**. Your laptop's address is already there from Week 9. Render's is not, and you have two choices:

   - **Render's outbound IP ranges, if your service shows them.** In the Render dashboard, open your web service (after step 2 below), open the **Connect** menu at the top right, and choose the **Outbound** tab. Add each range to Atlas: **Database & Network Access**, **IP Access List**, **Add IP Address**, paste the range, **Save and Close**. These ranges are shared by every Render service in the same region, so other Render customers can also reach the login prompt of your cluster, but the rest of the internet can't. If the **Outbound** tab doesn't list ranges for your free service, use the next option.
   - **`0.0.0.0/0`, access from anywhere.** Some free setups use this when the outbound ranges aren't available, or change. It means any computer on the internet can try to log in to your database, and the username and password are the only thing stopping them. Atlas emails every project member when someone adds it. If you use it: give the production user a long random password, never commit the connection string, and remove the entry when the course is over.

4. **Seed the production database** if you want the demo data there. From your laptop (whose IP is already allowed), in the `api` folder:

   ```bash
   MONGODB_URI="mongodb+srv://campus-events-render:PASSWORD@cluster0.abcde.mongodb.net/campus_events?retryWrites=true&w=majority" npm run seed
   ```

   `npm run seed` deletes every user, event and RSVP in that database first. Never run it against a database with real data.

## 2. Render: the API

`render.yaml` in this folder describes the service, so Render can create it for you (a "Blueprint").

1. Push the code to GitHub.
2. In the Render dashboard, choose **New**, then **Blueprint**, and **Connect** the repository.
3. Give the Blueprint a name and pick the branch. This repository keeps the file at `week13-deployment/render.yaml`, so type that in the **Blueprint Path** field. (In your own project, put `render.yaml` at the repository root and leave the field as it is.)
4. Render asks for the two values marked `sync: false`. It only asks when the Blueprint is first created; to change them later, use the service's **Environment** settings:
   - `MONGODB_URI`: the connection string from section 1.
   - `SESSION_SECRET`: run `npm run generate-secret` and paste the output. Use a different value from your laptop's `.env`.
5. Review the changes and click **Deploy Blueprint**.

What `render.yaml` sets up:

| Setting | Value | Why |
|---|---|---|
| `runtime` | `node` | Node version from `.nvmrc` (`24`) and `engines` (`24.x`) |
| `plan` | `free` | Leave it out and Render creates a paid instance |
| `region` | `virginia` | Close to Toronto and to Atlas in AWS `us-east-1` |
| `rootDir` | `week13-deployment/api` | The folder with `package.json` |
| `buildCommand` | `npm ci` | Installs exactly what `package-lock.json` lists |
| `startCommand` | `npm start` | `node --env-file-if-exists=.env src/server.js`. There is no `.env` on Render, so the variables come from the dashboard. |
| `healthCheckPath` | `/api/health` | A deploy only goes live once this answers 2xx or 3xx |
| `NODE_ENV` | `production` | `Secure` cookie, `upgrade-insecure-requests` |
| `TRUST_PROXY` | `1` | Render's load balancer handles HTTPS in front of the app |

You don't set `PORT`. Render sets it (to 10000 unless you change it) and the app already reads `process.env.PORT`.

When the deploy finishes, open `https://campus-events-api.onrender.com/api/health` (with your service's name). You should see:

```json
{ "status": "ok", "database": "connected" }
```

### Things to know about Render's free plan

- **Sleeping.** After 15 minutes without traffic the service spins down, and the next request takes about a minute while it starts again. Before a demo or a walkthrough, open `/api/health` a couple of minutes early. The web app's Server Components wait up to 60 seconds for the API (`web/lib/events.js`), and the events list shows "Loading events..." meanwhile.
- **750 free instance hours per workspace per month.** One service running all month fits. Time asleep doesn't count.
- **No permanent disk.** Files the app writes are lost on every deploy, restart and spin-down. Images uploaded through the admin form go to `uploads/`, so they disappear. Real apps store uploads in object storage (such as Amazon S3 or Cloudinary), which this course doesn't cover.
- **Deploys and SIGTERM.** A new deploy starts a new instance, sends it traffic once `/api/health` is healthy, then sends `SIGTERM` to the old one, followed by `SIGKILL` about 30 seconds later. `src/server.js` handles `SIGTERM`: it stops accepting connections, lets requests in progress finish, closes MongoDB, and exits.
- **Health checks.** Render expects a 2xx or 3xx within 5 seconds. `/api/health` answers 503 while MongoDB is disconnected. After 15 seconds of failures Render stops sending traffic to the instance, and after 60 seconds it restarts it. A new deploy that never becomes healthy is cancelled, and the previous version keeps running.

### Reading the logs

Open the service and choose **Logs**. **Live tail** shows new lines as they arrive. Every request is one line, ending with `req.ip`:

```
POST /api/auth/login 200 212ms 203.0.113.45
GET /api/events?sort=startsAt&page=1&limit=6 200 18ms 3.215.x.x
```

Startup problems show up here too: `MONGODB_URI is not set`, `SESSION_SECRET is not set`, or `Could not connect to MongoDB`.

## 3. Vercel: the web app

1. In the Vercel dashboard, choose **Add New...**, then **Project**, and **Import** the Git repository.
2. Next to **Root Directory**, click **Edit** and choose `week13-deployment/web` (in your own project, `web`). Vercel detects Next.js as the framework.
3. Open **Environment Variables** and add, before the first deploy:

   | Name | Value |
   |---|---|
   | `API_ORIGIN` | `https://campus-events-api.onrender.com` (your Render URL, with no `/api` and no trailing slash) |

4. Click **Deploy**.

`API_ORIGIN` must exist before the build, not only when the site runs. `next build` writes the rewrites into the build output, so the build decides where `/api` requests go. `next.config.mjs` stops a Vercel build that has no `API_ORIGIN`, with the message `API_ORIGIN is not set`, instead of producing a site whose API calls all fail.

The Node.js version comes from `engines` in `web/package.json` (`24.x`), which overrides the project's Node.js setting. Vercel supports 24.x.

### Changing an environment variable later

Changing a variable in the project's **Environment Variables** settings does not change the site that is already deployed. Vercel applies new values to new deployments only. After saving, go to **Deployments**, open the menu (the three dots) on the latest deployment, choose **Redeploy**, and confirm. For `API_ORIGIN` this is the only way the rewrites pick up the new value.

### Reading the logs

- **Build logs:** open a deployment and choose **Build Logs**. A failed build (a lint error, `API_ORIGIN is not set`) is explained here.
- **Runtime logs:** choose **Logs** in the project sidebar. Errors thrown in Server Components, such as `The API answered 500 when loading events`, appear here. The Hobby plan keeps runtime logs for 1 hour, so look soon after the problem happens.

## 4. Check the deployed app

1. `https://campus-events-api.onrender.com/api/health` answers `"database": "connected"`.
2. `https://your-app.vercel.app/events` lists events. The first visit after a break can take about a minute.
3. Register or log in (`ava@example.com` / `campus-demo-ava` if you seeded). In the browser devtools, open **Application**, then **Cookies**: `campus.sid` is set for `your-app.vercel.app`, with **HttpOnly** and **Secure** ticked.
4. Create an event and RSVP to it.
5. In the Render logs, the login line ends with your IP address. Open the site on your phone over mobile data and log in again: the new line should show a different address. If every line shows the same address, all visitors share one rate limit (see below).

## 5. Cookies, proxies and rate limits in production

- **Why `TRUST_PROXY=1`.** Render's load balancer receives the HTTPS connection and passes the request to your app as plain HTTP, with forwarding headers that say the original request was HTTPS and where it came from. Render's docs don't list the exact headers, so confirm the result in the logs (step 5 of section 4). With `trust proxy` set, Express believes those headers: `req.secure` becomes true, so express-session sends the `Secure` cookie, and `req.ip` becomes the address the proxy saw. Without it, login answers 200 but no cookie is set, and the user looks logged out on the next request.
- **Why the value is 1.** It is the number of proxies Express should trust, counted from the app outwards. Render's own documentation examples use 1. A higher number than the real count lets a client add its own `X-Forwarded-For` value and pick its IP address.
- **Rate limits behind the Vercel rewrite.** Browser requests to `/api` reach Render from Vercel's servers, not from the visitor. Vercel documents that it adds forwarding headers, but not exactly what an external rewrite target receives, so check it in the Render logs (step 5 of section 4). If every request shows the same address, every visitor shares the 10-attempt login limit. The fixes are to count the forwarded client address correctly (adjusting `TRUST_PROXY` to the real number of proxies), or to key the login limiter on something other than the IP address.
- **Caching.** Vercel caches responses from an external rewrite when they carry caching headers (for projects created on or after April 6, 2026). The API sends `Cache-Control: no-store` on anything for a logged-in user and no caching headers on the rest, so nothing is cached. Never add `Cache-Control: public` to a response whose content depends on who is asking.
- **Timeouts.** Vercel waits up to 120 seconds for the rewrite target to answer, longer than a Render cold start.

## Troubleshooting

| What you see | Likely cause | What to do |
|---|---|---|
| Browser console: `blocked by CORS policy` | The front end calls the Render URL directly (`fetch('https://...onrender.com/api/...')`) instead of `/api/...` | Use relative `/api/...` paths so the rewrite handles the request. Only if you really need direct calls, list the site's origin in `CORS_ORIGINS` on Render, and expect cookie problems (see Week 12). |
| `/api/...` requests on Vercel answer 502 or `ROUTER_EXTERNAL_TARGET_ERROR` | `API_ORIGIN` is wrong (a typo, `http` instead of `https`, an extra `/api`), the Render service failed to deploy, or the API took more than 120 seconds | Open `API_ORIGIN/api/health` in a browser. Fix the value in Vercel and redeploy, or fix the Render deploy (check its logs). |
| Vercel build fails with `API_ORIGIN is not set` | The variable is missing, or only set for Preview | Add it for Production and redeploy |
| You changed `API_ORIGIN` but the site still calls the old API | Environment changes don't reach existing deployments, and the rewrites are fixed at build time | Redeploy |
| Login says 200, but the header still shows "Log in" and there is no `campus.sid` cookie | `TRUST_PROXY` is missing on Render, so express-session refuses to send the `Secure` cookie | Set `TRUST_PROXY=1` on Render and deploy again |
| Render logs a `ValidationError` with code `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` | Requests arrive with `X-Forwarded-For`, but Express isn't trusting the proxy, so the rate limiter can't read the client address | Set `TRUST_PROXY=1` on Render and deploy again |
| The cookie appears for `onrender.com` instead of `vercel.app` | The login form posted to the Render URL directly | Post to `/api/auth/login` on the Vercel site |
| Render logs `Could not connect to MongoDB: Server selection timed out`, and the deploy never goes live | Render's addresses aren't on the Atlas IP Access List, or the cluster is paused | Add Render's outbound ranges (or `0.0.0.0/0`, knowing the risk), resume the cluster if it is paused, then deploy again |
| Render logs `bad auth : authentication failed` | Wrong database user or password in `MONGODB_URI`, or a special character in the password that isn't percent-encoded | Check the user in Atlas, and encode the password (Week 9 Atlas guide) |
| Render logs `SESSION_SECRET is not set` and the service exits | The variable was never set on the service | Add it in the service's environment settings and deploy again |
| The first page after a break takes about a minute, or shows "Something went wrong" with a Try again button | The free Render instance was asleep | Wait for it to wake, then press Try again. Open `/api/health` a few minutes before a demo. |
| Everyone gets `429 Too Many Requests` on login | All visitors reach the API with the same `req.ip` | Read section 5 and check the addresses in the Render logs |
| Images uploaded through the admin pages disappear | Render's free plan has no permanent disk | Expected on the free plan. Use image URLs, or object storage in a real app. |
| The Atlas cluster doesn't respond after a few weeks without use | Free clusters pause after 30 days with no connections | Resume it in Atlas |
